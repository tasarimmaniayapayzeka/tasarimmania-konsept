01

Who Chooses the Technology, and How?

The choice of language and stack isn't arbitrary — it rests on an analysis of the technical requirements.

The number of concurrent users, the volume of data, the integration requirement with existing systems and the hosting environment are all assessed at the outset. For a dealer panel with heavy transaction traffic, for instance, a Node.js or .NET-based architecture may suit; for a structure needing complex reporting, PHP/Laravel with a relational database (PostgreSQL, MySQL) may be preferred. The API layer is usually built over REST or GraphQL, so a mobile app or third-party systems can connect easily later on. The chosen language, versions and libraries are documented in writing in the technical specification; the decision isn't one-sided — your team's existing setup and your future growth plans are brought into it too.

02

Running the Project: From Analysis to Delivery

The project starts with a detailed analysis that maps out the workflows; the screens, roles and data models are settled at that stage.

Development runs in small, testable pieces, and every stage is shared with you in a staging environment first. Alongside functional testing, load testing and basic security checks are part of the process. Nothing goes live until user acceptance testing (UAT) is complete. Code is versioned with Git, so every change is traceable and can be rolled back if needed. At delivery the source code, technical documentation and a user guide are handed over together; throughout, a project lead acts as your single point of contact. Customer records held in the panel are personal data; the KVKK obligations on data controllers go into the design.

FAQs

Frequently asked questions: the bespoke software development process

When is bespoke software needed, and when does an off-the-shelf system fall short?

Off-the-shelf systems like WordPress or WooCommerce serve standard e-commerce and content needs well, but once business-specific logic comes into play — a dealer hierarchy, custom approval flows, multi-layered permissions — plugin solutions stop being enough. If your process doesn't fit standard patterns, or the system will need to talk to other platforms in future, bespoke software is the more sustainable option.

Which programming languages is bespoke software built in, and who chooses?

Depending on what the project needs, technologies such as Node.js, .NET or PHP/Laravel can be used; the choice is made by weighing performance, integration requirements and your team's existing setup together. The decision is presented with its reasoning in the technical analysis report, and development doesn't start without your sign-off.

Who maintains and updates the bespoke software after delivery?

Because the source code and documentation are handed over in full, your own team can take on maintenance. If you'd rather, we can carry on with security patches, performance work and new modules under a separate maintenance agreement.

How is integration with our existing systems (accounting, ERP, CRM) handled?

Integration is usually handled by a middle layer built over an API or webhooks; that layer maps the data formats between the different systems. Where the accounting, ERP or CRM side has no open API, secure synchronisation at database level is considered as well.

How is the timeline for a bespoke software project set?

The timeline is settled at the end of the technical analysis, according to the number of modules, the complexity of the integrations and the variety of screens and roles. The firm schedule and delivery plan come with the quote shared in the pricing section, once the scope is settled.

Who owns the source code and the intellectual property?

When the project is delivered, the intellectual property in the source code, the design files and the documentation is transferred to you. That transfer is set out explicitly in the contract, so you can carry your software on with another team whenever you like.

The detail

If you'd like to look before deciding

  1. 01

    Dealer Panels and Permissions

    Panels are built where different dealer, regional or departmental roles each work within their own permission boundaries. Viewing, approval and reporting rights are defined separately for every role, so the central team can watch the whole network from one point.

  2. 02

    Booking and Appointment Automation

    Booking systems are built that prevent calendar clashes, send automatic notifications and handle capacity planning. The system is set up to share the same database as your existing website or mobile app.

  3. 03

    The ERP/CRM Integration Layer

    An integration layer is built between your accounting, stock or customer management systems and the processes on the web side, preventing duplicated data. That layer keeps order, stock and customer information current from a single source.
